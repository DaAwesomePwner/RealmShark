### Task 2: `LootCapture` and `LootFilters`

**Owns:** see the file map. **Reads:** R1 §0.3, §1.1, §4.2; R3 §3.3 (the `LootGUI` row).

- **`LootFeed`-style extraction in `LootDashboard`:** the live loot state (today's private `State`, `receive(...)` including `AppHistory.append("loot", drop)`, the refresh queue) becomes a headless public nested class `LootDashboard.Feed` that never touches Swing except through `invokeLater` to its attached views. `new LootDashboard(Feed)` attaches a view (public); `new LootDashboard()` keeps a private feed (tests). Add `long Feed.revision()` (bumped per received bag) and `List<LootFacts.Bag> Feed.snapshot(String session)` (a detached copy of `state.recent`, at most `RECENT_LIMIT` bags, projected with `LootFacts.bag(session, drop)` under the state lock) plus `boolean Feed.capped()`. `LootDashboard.receive(...)` keeps compiling and delegates to its feed. `LootDashboard.Drop`, `LootDashboard.Item` and their fields keep their names and package (Task 3 reads them).

Entry points: `update(map, bag, dropper, player, time[, context])` and `updateExaltStats()`, with today's `player == null || !update` gate. It publishes each accepted drop to registered sinks (`addSink(LootSink)`, called on the capture thread; sinks only hand off), so the Live log keeps working until Task 12. Package-private constructor with injectable `SendLoot.Session`, sound player, scheduler and delay for tests.
- **`LootGUI`:** its static API (`update`, `updateExaltStats`, `lootSharing`, `applyFilters`) delegates to `LootCapture`/`LootFilters`, so `TomatoData` needs no change; `update` no longer throws when no `LootGUI` was built.
